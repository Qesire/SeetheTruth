# SeetheTruth 全站人机交互与科研可视化审查

**范围**：`Qesire/SeetheTruth`，共 20 个公开 HTML 页面、17 个统一注册的专项实验室，以及 PC/Android 同源教学中心。  
**依据**：已安装的 `interface-design`、`scientific-visualization`、`research-implementation` 和 `evidence-analysis` 技能；实际页面 HTML/CSS/JS、`learning_experience_core.js`、现有 Chromium/Android 测试与截图。  
**审查性质**：本文件记录具体源码问题、已经写回的交互修订和需要真实使用者完成的任务。静态源码审阅与浏览器检查均不能替代 Android 真机和非作者使用测试。

## 一、用户如何在系统中前进

当前应用承载三种关系不同的任务：

- **建立模型认识**：课程中心 → 自由积木 → 单算子/单张量/单坐标。这一路径需要可读的图、明确的形状和结果状态。
- **验证机制与工程决策**：架构比较、训练循环、KV Cache、DeepInfer Scheduler/Worker、Wan FFN 等专项计算。它们运行各自真实的教学数值或状态机，而非全部强制转换为 Tensor DAG。
- **判断研究证据**：静态源码、解析成本、合成计算、来源绑定的真实模型 Trace 和实际 Telemetry 必须保持不同证据等级。图形颜色与数字只有在来源、单位和统计量一致时才有科学含义。

课程中心是发现入口；积木工作台承担自由组合；专项实验室负责各自的算法与状态；证据页面标明其输入 provenance。页面之间的连接由现有 `Core.labs` 与源驱动课程清单提供，审查不建立第二套运行时或模态数据库。

## 三、整体设计改动

**第一层：发现与返回。** 每个公开页面都提供通向统一课程中心的路径。模型图谱与学习工作台只把当前任务放在顶部，次要模块以可展开菜单进入。课程中心的专项目录直接读取 `Core.labs`，不会出现与运行时注册身份脱节的第二套跳转表。

**第二层：操作与反馈。** 所有页面共享 `ui_accessibility.css` 的键盘焦点与“跳到主要内容”入口；原页面各自的数据输入、状态变化和提示仍由专业模块管理，不用统一装饰层替代真实反馈。手机端学习工作台提供明确的画布直达操作。训练状态重置披露具体丢失内容。

**第三层：科研语义。** 热力图和直方图提供读屏名称，页面继续区分声明、固定样例、来源计算和可测数据。CI 只能证明有对应行为的路径；假设输入、解析成本和小张量数值不升级为性能实测或模型能力证据。

## 四、验收与未解决问题

新建 `tests/sitewide_ui_contracts.js` 验证 20 个页面的主内容标记、课程回路、键盘跳转、专项目录来源与 Android 离线边界。`tests/browser_sitewide_ui_audit.py` 在真实 Chromium 中逐一打开全部 20 页的 1440px 和 390px 视口，总计 **40 个首屏观察**，记录页面宽度、导航、按钮可访问名称、脚本报错及截图。图像由该工作流产出并且与提交 SHA 绑定；需要以其实际运行输出决定哪些模块仍有严重裁切或无效导航。

自动化之外还有三个明显的 Beta 证据缺口：Android 真机触控/系统 WebView；非开发者完成从课程到计算图再到结果解释的任务；WebGL 模型图谱与长时序表格在不同缩放级别和辅助技术下的可读性。尤其是横向滚动画布，不能以“全文档宽度不溢出”简单判错，需要分离局部可滚动容器与页面级非预期溢出。

正式发行还需项目所有者确定许可证或分发授权，合并后在 `main` 与标签上重新验收。现阶段适合内部 Alpha 审查，不以静态审阅取代发布授权。

## 五、下一轮任务型用户测试

选择不同熟悉度的参与者，固定课程版本和设备宽度，观察以下完整任务：从课程中心找到一个机制；运行原生数值；选中真正产生结果的节点；从两个运行条件解释差异；修改错误条件并恢复；返回另一个相关实验室。记录**完成/失败、误操作、求助点与任务耗时**，且把一次参与者而非其每次点击作为独立的行为观测单位。对于图形可读性，再记录首次能指出当前 Step、来源/数值口径和结果单位的位置。

这批任务直接决定是否可以将“可运行实验”提升为“新用户可理解并完成”的教学 Beta 主张。

## 本地首屏复核补充（2026-11-11）

在与 PR 提交对应的源码快照上，使用独立 Chromium 的 `set_content` 和内嵌静态资源检查首屏几何；该环境阻止了 `file://` 与本机 HTTP 导航，因此这项检查仅证明 **CSS/DOM 可见布局**，专门的实验室脚本会因为 `about:blank` 路由而产生非产品性错误，不将其计为生产运行证据。已观察到的布局：`index.html` 在 390px 屏幕出现了 **58px 非预期文档横向溢出**；重排顶部三项主要操作后，重新测得 `document.documentElement.scrollWidth=390`，顶部入口全部落入屏幕。对其他各首屏的同类局部检查未测出整页溢出。正式验收仍由真正本机 HTTP 的 CI Chromium 访问与截图决定。对全站新增整页水平溢出的浏览器失败断言，容许局部横向滚动区域存在。

### 移动端工作台的实际滚动距离

直接渲染 390px Chromium 首屏时，原有 `learn.html` 的 `.stage` 位于页面约 **11,060px** 纵坐标；点击补充的“查看当前计算图”才能跳过长目录。按界面设计技能的主任务优先原则，现将手机布局改成 **当前计算图 → 课程/积木目录 → 数值检查器**，既有 DOM 节点、课程注册和数值算法不变。桌面维持原三栏。手机标题栏新增“选择课程／积木”，允许从图返回目录。离线 Chromium CSS 验证新 `.stage` 起始纵坐标约 **229px**，页面宽度仍为 390px；最终真实 HTTP 页面交互由 CI 的 390px 浏览器测试证实。

### 展开菜单的真实点击验证

在源码快照的 Chromium 渲染中，模型图谱的 `数据与工具` 虽然能展开，但 `#importOpen` 的真实鼠标点击被 `.layout .mechanism-section` 拦截，Playwright 等待超时。该问题源自菜单可见性与父级 stacking context 的顺序不同；新 `ui_accessibility.css` 仅在 `details[open]` 时提升 `.header` 和菜单层级。修复后本地 Chromium 对模型图谱 `#importOpen` 与学习工作台 `cache.html` 链接均完成真实点击；CI 将用实际模态弹窗出现判定可操作性。已有的首页导入测试更新为先展开“数据与工具”，然后点击原 `#importOpen`，仍执行原来的导入及错误输入测试。
